# SmartStore in Splunk Enterprise

## What SmartStore does

SmartStore decouples compute and storage for indexed data.
Indexer nodes still perform indexing and searching, but warm bucket master copies are stored in remote object storage (S3, Azure Blob, GCS), while local disk is used as cache.

<img src="/static/app/splunk4champions2/images/smartstore_classic_vs_modern.png" width="100%" alt="Classic Splunk architecture: indexer with Hot/Warm, Cold, and Frozen to S3 archive. SmartStore: indexer with local Hot/Cache under cache manager and warm masters in S3-compatible object store" />

**Reading the diagram:** the classic side keeps **hot/warm**, **cold**, and **frozen** on indexer-coupled storage (frozen often means an archive destination such as S3). The SmartStore side keeps **hot/cache** locally—governed by the **cache manager**—and **warm** masters in an **S3-compatible API** object tier (Azure Blob and GCS are supported too). Splunk documents the same storage-option contrast under <Link to="https://lantern.splunk.com/Splunk_Success_Framework/Platform_Management/Indexing_and_search_architecture" openInNewContext>Splunk Lantern: Indexing and search architecture</Link>.

Core idea:
- **Hot** data is local and writable.
- Rolled **warm** buckets are uploaded to remote object storage.
- Local cache keeps frequently searched data nearby.
- Missing warm buckets are fetched on demand by cache manager.

## SmartStore lifecycle (simplified)

| Step | Behavior | Searchable |
|---|---|---|
| Hot | New events are indexed locally | Yes |
| Warm (remote master) | Warm bucket master lives in object store | Yes |
| Cache | Local copy kept based on cache policy and search demand | Yes |
| Frozen | Data ages out based on retention policy | No |

### Important difference from traditional model

Traditional retention usually follows:
**hot -> warm -> cold -> frozen**

SmartStore-enabled indexes are commonly operated as:
**hot -> warm (remote master) -> frozen**

Cold is often unnecessary because warm buckets already live in low-cost object storage.

## Cluster behavior (high level)

For SmartStore indexes in clusters:
- Replication/search factor semantics differ from non-SmartStore warm buckets.
- Remote storage is the source of truth for warm-bucket data.
- Peers rely more on metadata + cache behavior than on storing many local warm copies.

This is where much of the local disk saving comes from.

## SmartStore vs frozen archive on S3

These two are often confused:

- **SmartStore S3**: active warm-bucket master storage (searchable via cache retrieval)
- **Traditional frozen archive on S3**: aged-out data archive after retention

Same backend technology, very different role in the lifecycle.

## Library analogy

<img src="/static/app/splunk4champions2/images/library.jpg" width="80%" alt="SmartStore library analogy" />

Think of SmartStore like a library:
- **Reading desk** = local cache (fast access)
- **Bookshelves** = remote object storage (long-term, large capacity)
- **Librarian** = cache manager (fetches what you need, when you need it)

Result: most data stays searchable without keeping everything on local disk.
