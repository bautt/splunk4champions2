## Data lifecycle (traditional index storage)

<img src="/static/app/splunk4champions2/images/data_retention_lifecycle.png" width="100%" alt="Data retention lifecycle illustration: hot, warm, cold, frozen, thawed" />

### Overview

In traditional Splunk Enterprise index storage, data ages through bucket states:
**hot -> warm -> cold -> frozen** (and optionally **thawed** after restore).

- New events are written to **hot** buckets.
- Full hot buckets roll to **warm**.
- Older warm buckets roll to **cold**.
- Retention policies eventually move data to **frozen**.
- If archived data is restored, it appears as **thawed**.

By default:
- `db` path: hot + warm
- `colddb` path: cold
- `thaweddb` path: restored thawed data

### Bucket states at a glance

| State | What it means | Searchable |
|---|---|---|
| Hot | Active write target for new events | Yes |
| Warm | Rolled from hot; no longer written, still searchable | Yes |
| Cold | Older searchable buckets moved off hot/warm storage | Yes |
| Frozen | Data aged out of index; deleted or archived | No |
| Thawed | Archived data restored back for investigation | Yes |

### Retention controls that matter most

Two main controls determine when data is retired:

- `frozenTimePeriodInSecs`  
  Maximum age before data is frozen.
- `maxTotalDataSizeMB`  
  Maximum index size; oldest data is frozen first once exceeded.

Important: whichever limit is hit first wins.  
So data can age out by **size pressure** before it reaches the time-based retention target.

### Where S3 fits in the traditional model

In the traditional model, S3 (or other object storage) is typically used as a
**frozen archive destination**, not as active searchable storage.

That is different from SmartStore, where remote object storage holds active warm-bucket master copies.

Splunk Lantern’s <Link to="https://lantern.splunk.com/Splunk_Success_Framework/Platform_Management/Indexing_and_search_architecture" openInNewContext>Indexing and search architecture</Link> article lays out the same comparison: classic file-system tiers versus SmartStore’s SSD-style **local cache** plus **warm** data in remote object storage (often with no separate **cold** tier).
